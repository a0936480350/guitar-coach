## D-0001 · 和弦對錯用「聽」的判斷，不用「看」的

**日期**：2026-08-16
**狀態**：已採用

### 背景

Google Drive `21.Side Project Idea/` 的規劃書（`.pptx` 與 `.md`）提出的 MVP 第一步是：

> 用 Claude Code 在 Web 端做出 MVP：MediaPipe.js 抓手部關鍵點 ＋ 簡單比對邏輯
> ＋ 畫面上顯示「對／不對」

規劃書把這一步當成**最簡單、風險最低**的起點。

### 問題

這一步其實是全案**最難**的部分。

MediaPipe 回傳的是 21 個關鍵點在**畫面上的 2D 正規化座標**。
但「食指按在第 5 弦第 2 格」是**吉他座標系**的資訊。要從前者推到後者，必須先解決：

1. **琴頸定位** —— 畫面中琴頸、琴衍、琴弦在哪。MediaPipe 完全不提供這個能力
2. **相機角度** —— 攝影機偏移十幾度，同一個手勢對應到的格子就變了
3. **遮擋** —— 按和弦時手掌會蓋住指尖，關鍵點直接消失或亂跳

這三項合起來是研究等級的題目，不是「簡單比對邏輯」。
把它排在第一步，等於把全案唯一的致命風險放在最前面，而且沒有備案。

### 決定

**M0 改成音訊和弦辨識**，視覺往後移到 M1，且 M1 只做音訊做不到的事。

| | 視覺判和弦 | 音訊判和弦 |
|---|---|---|
| 相機角度影響 | 致命 | 無 |
| 遮擋問題 | 有 | 無 |
| 演算法成熟度 | 研究題目 | 成熟（chroma + 範本比對） |
| 量到的東西 | 手看起來像對的 | **它聽起來是對的** |

最後一列是決定性的：學生要的不是「手擺得像教材照片」，是**彈出來的聲音對**。

### 視覺該做什麼

視覺留給音訊聽不出來的東西 —— 手腕彎折角度、拇指是否越過琴頸、手指有沒有立起來。

關鍵在於：**這些只需要關節之間的相對角度，不需要知道琴頸在哪。**
所以它避開了上面三個難題，技術上完全可行。

### 修正既有文件

`xian-knowledge-os/projects-incubator/guitar-hand-coach-可行性研究.md` 原本把
「音準」整個歸在研究級的第三層。這需要再切細：

- 「這個和弦按對了嗎」—— 受控條件下（單把吉他、安靜環境、已知的少數和弦）**可行**
- 「音色好不好、律動有沒有味道」—— 研究級，維持不碰

### 後果

- 好處：第一個能動的東西一個週末就出得來，而且核心風險提早驗證
- 代價：暫時給不出「你第三根手指壓到第二弦了」這種指法級回饋
- 這個代價可接受 —— 那種回饋本來就要等琴頸定位解決，不是這個階段的事

## D-0002 · DSP 核心與 UI 分離

**日期**：2026-08-16
**狀態**：已採用

`src/chroma.js` 是純函式，不碰 DOM、不碰 `getUserMedia`、不碰 `AudioContext`。

**理由**：同一份程式碼要能吃兩種輸入 —— 麥克風即時音訊、離線合成的測試音。
分離之後可以在**沒有吉他、沒有麥克風**的情況下用 `npm test` 驗證演算法。

這對 side project 特別重要：改動後不用每次都拿起吉他才知道有沒有壞掉。

**代價**：多一層抽象。但這裡的抽象是真的有用途，不是為了漂亮。

# guitar-coach · 吉他練習即時回饋

學生沒有老師在旁邊時，也能知道「我彈的對不對」。

**目前狀態：M0（音訊和弦辨識）可跑，已用合成音驗證 9/9。**

---

## 為什麼先做「聽」而不是「看」

原始規劃是先用鏡頭抓手部關鍵點，比對標準按法，判斷和弦對不對。
評估後把順序換掉了，理由是：

MediaPipe 給的是 **21 個關鍵點在畫面上的 2D 座標**，但「食指按在第 5 弦第 2 格」是
**吉他座標系**的資訊。要從前者推到後者，必須先偵測琴頸/琴衍/琴弦在畫面中的位置、
處理相機角度、處理手掌對指尖的遮擋 —— 這是研究等級的題目，不是「簡單比對」。

而「和弦對不對」用聽的：

| | 用看的 | 用聽的 |
|---|---|---|
| 相機角度影響 | 致命 | 無 |
| 遮擋問題 | 有 | 無 |
| 演算法成熟度 | 研究題目 | 成熟（chroma + 範本比對） |
| 量到的東西 | 手看起來像對的 | **它聽起來是對的** |

最後一行是重點：學生要的不是「手擺得像照片」，是彈出來的聲音對。

**視覺留給音訊做不到的事**（M1）：手腕彎折角度、拇指是否越過琴頸、
手指有沒有立起來。這些只需要關節之間的**相對角度**，不需要知道琴頸在哪
—— 技術上完全可行，而且是老師最有價值的判斷。

## 跑起來

```bash
npm test        # 合成和弦驗證 + 走鐘檢查（不需要吉他也不需要麥克風）
npm run serve   # 開 http://localhost:4173
```

麥克風需要 `localhost` 或 HTTPS，直接用 `file://` 開會被瀏覽器擋掉。

## 檔案

| 檔案 | 作用 |
|---|---|
| `src/chroma.js` | 辨識核心。純函式，不碰 DOM 與麥克風 —— 所以可離線測試 |
| `src/selftest.mjs` | 合成 9 個開放和弦（含泛音）→ DFT → 辨識，驗證演算法 |
| `index.html` | 網頁 UI（模組版，本機開發用） |
| `standalone.html` | **單一檔案版** — 給 Artifact 用，可直接開連結測試 |
| `src/drift-guard.mjs` | 擋 `standalone.html` 與 `chroma.js` 的和弦定義走鐘 |

把 DSP 核心跟 UI 拆開是刻意的：同一份程式碼既吃麥克風的即時音訊，
也吃合成出來的測試音。**沒有吉他也能證明演算法會動。**

## 目前的辨識範圍

9 個開放和弦：`C D E F G A Am Em Dm`

範圍小是刻意的 —— 辨識 24 個和弦的準確率遠低於辨識 9 個。
先把常用的做準，再談擴充。

### 自我測試結果

```

```

第二名都是音樂上本來就該接近的和弦（Em↔E、Am↔A、C↔Am、D↔Dm），
代表演算法行為合理，不是碰巧猜中。

**但這是合成音的結果。真吉他還沒測過** —— 真實錄音有房間殘響、
琴弦不準、雜訊、破音，準確率一定會掉。這是下一步要面對的事。

## 真正的門檻不是技術

抓關鍵點、算角度、比對範本，這些工程師都做得到。
做不到的是**定義吉他的對錯** —— M1 每一條規則（手腕彎幾度該提醒、
拇指到什麼位置算越頸）都需要教學經驗才給得出量化標準。

那部分不是寫程式能生出來的。
